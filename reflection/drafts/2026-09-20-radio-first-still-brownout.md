# Candidate retrospective: radio-first A/B still brownouts at PHY

- Evidence: the user's `e22382cf-959f-4f49-ad82-7e4bbb6f27fa` log was built at 11:14:40 from `687a064f-dirty`; it reaches SD mount and Web preparation, then starts Wi-Fi before any display/LVGL/service logs. Every shown attempt reaches `phy_init: phy_version ...` and immediately logs `E BOD`, with `rst:0x3` and `rtc_brownout_isr_handler`.
- Correction: the prior pre-PHY task-load hypothesis was a real software risk in the normal order, but this A/B removes that load and still fails at the same PHY boundary. It is not sufficient as the root cause.
- Deeper software candidates: ESP-IDF's `esp_phy_load_cal_and_init()` promotes partial calibration to full calibration when RF calibration data is absent/invalid in NVS; the paste does not reach the warning that would confirm this. The project also enables `CONFIG_ESP_PHY_REDUCE_TX_POWER`, but its first power-on cycle cannot use the conditional BOD reduction path. The later ROM `RTC_SW_SYS_RST` text is not enough to classify the application API reset reason because the brownout ISR writes an RTC hint. Modem power save is configured only after `esp_wifi_start()` returns.
- Isolation gap: this A/B still mounted SD before Wi-Fi (`app_startup_run()` calls `app_storage_boot_run_diagnostic()` before the Wi-Fi-first block), so it removed display/LVGL/service-task load but did not remove all pre-PHY peripheral load.
- Recurrence count: two confirmed software-order experiments (normal order and radio-first) fail at the same PHY/BOD boundary; the physical rail element remains unisolated.
- Proposed minimal rule: treat a radio-first A/B that still fails before `STA PHY bring-up complete` as evidence against scheduler/LVGL ordering, then test PHY calibration/USB-PHY configuration separately; do not keep moving application tasks or add larger bulk capacitors without a new boundary measurement.
