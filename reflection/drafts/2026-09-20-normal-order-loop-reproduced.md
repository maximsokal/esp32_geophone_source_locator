# Candidate retrospective: normal-order loop reaches PHY brownout

- Evidence: attachment `b6bc31ad-9b59-4463-8f91-13522c6905fe` shows three identical cycles from `687a064f-dirty`, compiled 11:41:04. Storage and object recovery finish; the CPU snapshot reports 94% Core 0 busy; Wi-Fi PHY starts at 4500 ms, prints `phy_version` at 4510 ms, then the brownout ISR resets the chip. There is no panic, watchdog, power-button shutdown, or `STA PHY bring-up complete`.
- Correction: `STORAGE_DIR: path-exists-lock-wait` is not the hang point. The lock wait is about 20 us, the stat completes in about 96 ms, and the recovery/service path reaches Wi-Fi normally. The display flicker is the visible consequence of repeated resets.
- Deeper result: the image was built with the one-shot `CONFIG_ESP_PHY_RF_CAL_NONE` diagnostic, yet the PHY boundary and BOD remained unchanged. Therefore the calibration routine is not sufficient as the sole software cause; the failure is associated with RF frontend bring-up or the rail/load path at that boundary.
- Recurrence count: normal order, radio-first with SD still mounted, and calibration-disabled normal order all reproduce the same PHY/BOD boundary. The remaining software isolation gap is a true Wi-Fi-only boot with SD and all peripheral initialization skipped, plus explicit reset-reason logging after reboot.
- Minimal rule: do not “fix” the recovery/stat path or keep moving LVGL tasks based on this log. Treat it as a brownout during `esp_wifi_start()`/PHY initialization; use a clean software isolation build and rail measurement before further boot-order edits or larger capacitors.
