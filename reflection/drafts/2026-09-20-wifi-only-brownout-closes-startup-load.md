# Candidate retrospective: reduced startup still brownouts at PHY

- Evidence: attachment `6a712f2b-8c53-4055-9230-213362e3887a` (`687a064f-dirty`, compile 12:52:32) contains no display, SD, storage, recovery, AD7606, INA3221, TCA, or service initialization before `WIFI_STA: STA PHY bring-up begin`. It reaches `phy_init: phy_version` and immediately logs BOD; no PHY-complete line appears. Later cycles brownout even earlier while the rail is recovering.
- Correction: the earlier claim that Core 0 saturation or the pre-PHY application workload is the root cause is closed. Those code paths are absent from this image and the boundary remains.
- Remaining isolation gap: the reduced image still runs core setup, including GPIO/keypad and SPI2 safe levels, and the physical modules may remain connected. Driver omission is not the same as electrical disconnection.
- Recurrence count: normal order, radio-first with SD mounted, calibration diagnostic, and reduced startup all fail at the same PHY boundary; only the first three contain the larger application workload. The radio transition itself is now the narrow software boundary.
- Proposed minimal rule: stop changing storage/LVGL/recovery ordering. Run the reduced image with every external module physically disconnected and, if needed, remove `app_startup_initialize_core()` from the diagnostic path. If the bare ESP32 still fails, instrument 3V3 during `esp_wifi_start()` or substitute the board/power path; if it survives, reconnect modules one at a time, starting with AD7606 because its powered/unpowered VIO backfeed was previously measured.
